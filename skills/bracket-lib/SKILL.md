# bracket-lib でローグライクを作る

ユーザーの既存の Rust プロジェクトに合わせて、依頼されたゲーム機能を実装・説明する。
説明は日本語を基本とし、コードの識別子と API 名は正式表記を使う。

## 対象を確認する

- プロジェクトの指示、README、進捗資料があれば従う。必要な見出しと範囲を読む。
- `Cargo.toml`、`Cargo.lock`、関連する Rust コードから、導入元・リビジョン・バックエンドを確認する。
- Cargo の依存名は `bracket-lib`、Rust の名前空間は `bracket_lib`。旧資料の `rltk` と区別する。
- GitHub 版と公開版は同じ `0.8.7` 表記でも実装が異なることがある。API は対象コミットのソースを優先して照合する。
- ユーザーから更新を依頼された場合に取得版を見直す。通常の機能追加のために依存関係や ECS を一律に入れ替えない。

## 実装で守る要点

- `State` などの構造体にゲーム状態を置き、`GameState::tick` を通じて描画と更新を行う。
- `tick` は毎フレーム呼ばれる。ターン制の敵行動は、入力に応じたターン消費と結びつける。
- 画面座標は左上原点、右が x 正方向、下が y 正方向。セル数とピクセル数を区別する。
- 描画は消去、地形、キャラクター、UI の順など、必要な重なり順に組み立てる。
- `ctx.key` の入力イベントと押下状態の継続監視を区別する。
- 配列添字への変換前に座標の範囲を確認し、移動先の壁・占有状態をゲームのルールに従って判定する。
- 視野の遮蔽は `BaseMap::is_opaque`、経路の通行可否とコストは `get_available_exits` に対応させる。
- A* の推定距離は移動方式とコストに合わせる。結果の成功と長さを確認してから次のセルを取り出す。
- `range(min, max)` は上限を含まない。再現が必要な生成ではシードと乱数の消費順を管理する。
- 標準 CP437 フォントに日本語表示を期待しない。日本語 UI の依頼ではフォントと文字割り当てを別途検討する。

## 確認して報告する

コードの変更や実行可能なサンプルは、対象プロジェクトの依存関係でコンパイルする。
計算だけの例は必要に応じて実行し、画面・入力の挙動は GUI で確認できた範囲を伝える。
ビルド成功だけでウィンドウ表示や操作を確認済みにしない。
進捗資料の更新ルールがある場合は、変更点・確認結果・残りの作業を記録する。
